# Autopilot 2.2.46 — фізичне очищення оперативної бази за сім діб

## Дефект
LIVE-телеметрія 28.10.2026 09:52 показала **2335 неопублікованих записів старших семи діб** і базу 103,24 МБ, хоча черга була нульова. Старий механізм RC103 обирав записи за датою публікації першоджерела, а операторський лічильник — за датою отримання до бази. Сторонні, неправильні та майбутні дати першоджерела могли залишати старі записи назавжди. Очищення виконувалося одноразово після запуску і не повторювалося протягом довгих сеансів.

## Що зроблено
- Єдиний критерій **дата додавання до локальної бази, старша 7 діб**, узгоджений з LIVE-телеметрією. Правила **публікацій лише поточної доби й лише після запуску** залишаються незалежно незмінними.
- У фоні після 5 хвилин роботи та кожні наступні приблизно 30 хвилин видаляються фізичні застарілі **оперативні** записи разом із каскадними завданнями/чорновиками, невеликими пакетами, із транзакцією на пакет і перевіркою дати безпосередньо перед видаленням. Не блокувати запуск UI/колекторів або надсилання Telegram.
- **COMMITTED**: зберігаються незмінні ідентифікатори підтверджених Telegram-доставок у `delivery_receipt_archive` завдяки існуючому BEFORE DELETE trigger. Подієва історія `event_publication_history` зберігається для захисту від дублювання. Оригінальний digest підтверджених доставок у тестах незмінний.
- **UNKNOWN / FAILED / PREPARED / SENDING**: не чіпати статті та журнали невизначених доставок, ніяких автоматичних повторів. Раніше ізольована UNKNOWN-доставка зберігає карантин.
- У поточних статей, які посилалися `duplicate_of` на очищений старий запис, посилання обережно обнуляється, без видалення нової статті.
- Не змінювати `published_dedupe_window_hours` або інші налаштування оператора. Не запускати `VACUUM`, примусове перемикання WAL чи побудову індексів у живій програмі. Видалені записи звільняють сторінки для повторного використання SQLite, тому **розмір файлу .sqlite3 може не зменшитися одразу**.
- У LIVE `database` додано `retention_eligible_over_7d`, `retention_protected_delivery_over_7d` і `retention_last_run` з фактичною кількістю очищених рядків і залишком. Старий `stale_unpublished_over_7d` лишається для порівняння і може включати захищені UNKNOWN-рядки.

## Приймання
- Регресії: записи зі старою датою надходження/майбутньою датою SOURCE, нові записи зі старою датою SOURCE, FK-safe видалення, спадковість COMMITTED SHA256, збереження UNKNOWN/FAILED/PREPARED/SENDING, реальні посилання на дублікати, повторний запуск без зайвих видалень, обмежені пакети, збереження операторського dedupe window.
- CI Ubuntu та Windows Python 3.11/3.12/3.13, Windows Portable GUI/Defender, контрольний SHA256, офіційний GitHub ZIP.
- При встановленні зберегти повністю стару `Data`, розпакувати нову версію в **окрему** папку, перенести всю `Data`, запустити один екземпляр. Після понад 5 хвилин перевірити `retention_last_run`, кількість залишених придатних старих рядків, цілісність `COMMITTED`, карантин `UNKNOWN`, 3/3 воркери/колектори і звичайні Telegram-доставки.
- **Ніякого стирання бази чи очищення налаштувань.** Фізичне зменшення розміру файлу SQLite не є приймальним критерієм роботи у живому режимі; важлива відсутність зайвих старих операційних записів і збереження підтверджених доставок.
